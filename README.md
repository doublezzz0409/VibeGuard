# VibeGuard

> "Vibecoding 太爽了，但它需要一个守卫。"

VibeGuard 是一套 Claude Code 自定义命令系统，通过契约驱动 + 多 Agent 协作 + 强制交叉校验，将 AI 生成代码从"看着能跑、实际不能用"转变为确定性交付。

## 核心问题

用 AI 写前端时，你一定遇到过：

- **按钮点击无效** — 组件的"壳"有了，但核心逻辑漏写
- **路由指向空白页** — 占位页面，核心内容缺失
- **字段前后端不一致** — 驼峰和下划线混用、Date/String 混乱
- **命名即兴发挥** — 交叉引用不可用，全靠 AI 当时的灵感
- **越补越乱** — 局部正确、全局不可维护的屎山

根本原因：**AI 单次执行没有全局约束力，模糊需求经过多层放大后变成不可维护的代码。**

## 解决方案

VibeGuard 用三个 `.md` 文件构建一套 AI 开发流水线：

```
naming-convention.md    ← 共享契约层（字段定义、命名风格、类型规范）
translate-requirement.md ← 需求精炼分析师（对话 A）
frontend-standard.md    ← 14 步强制执行引擎（对话 B）
```

### 架构总览

![VibeGuard Architecture](deepseek_mermaid_20260501_d0a23c.png)

系统包含 5 个 Agent 角色，通过共享契约文件联动：

| Agent | 职责 |
|-------|------|
| 需求分析师 | 将模糊需求翻译为精确规格说明 |
| 前端开发 | 按契约生成组件和页面 |
| 全栈开发 | 实现 API 路由和后端逻辑 |
| 测试工程师 | 执行功能测试和回归验证 |
| 后端文档工程师 | 维护 mock-api-doc 的全局一致性 |

所有 Agent 都从 `naming-convention.md` 加载契约，确保使用同一套字段名、类型和路由。

## 工作流程

整个流程分两个对话窗口执行：

### 对话 A：需求精炼（`/translate-requirement`）

```
用户："加个点赞功能"
        ↓
  加载已有契约（types.ts、mock-api-doc、命名规范）
        ↓
  追问三原则（假设反面 / 数据关联 / 类比建议）
        ↓
  基于命名规范推导实体名 → 字段名 → API 端点
        ↓
  冲突扫描（查重 types.ts、mock-api-doc、路由表）
        ↓
  输出：精确的需求规格说明
```

**关键约束：** 需求描述中禁止出现任何实现方案。"用户点击后数字加一"可以，"用 useState 管理计数器"不行。

### 对话 B：强制执行（`/frontend-standard`）

```
需求规格说明
        ↓
  14 步串行执行，每步强制输出完成标记
        ↓
  7 道拦截关卡：
    · 需求模糊 → 退回 translate-requirement
    · 命名冲突 → 退回修改需求
    · 格式歧义 → 要求明确字段精度
    · 路由缺失 → 执行路由契约清算
    · 字段割裂 → 交叉校验拦截
    · 文档局部化 → 全局完整性检查
    · 实现方案越界 → 自检拦截
        ↓
  发现契约冲突 → 立即停止，等待人类裁决
        ↓
  交付：类型 · Mock · 路由 · 组件 · 测试 · 文档 全链路同步
```

核心思想：**不信任 AI 的自觉，只信任对照结果。**

## 7 道拦截关卡

| 关卡 | 拦截什么 | 行动 |
|------|---------|------|
| 需求模糊 | 需求描述不完整 | 喂给 `/translate-requirement` 先跑精炼 |
| 命名冲突 | 新实体/字段与已有冲突 | 退回修改需求 |
| 格式歧义 | 字段类型未定义（如 Date/String 混淆） | 要求字段精度 |
| 路由缺失 | 新页面没有对应路由声明 | 执行路由契约清算 |
| 字段割裂 | 新旧需求的字段不统一 | 交叉校验拦截 |
| 文档局部化 | mock-api-doc 只改了一处 | 全局完整性检查 |
| 实现方案越界 | 需求描述中出现具体技术方案 | 自检拦截 |

## 安装

将命令文件复制到你的 Claude Code 项目命令目录：

```bash
mkdir -p .claude/commands
cp translate-requirement.md .claude/commands/
cp frontend-standard.md .claude/commands/
cp naming-convention.md .claude/commands/
```

## 使用

### 1. 初始化项目契约（一次性）

在 Claude Code 中让 AI 根据你的项目生成 `naming-convention.md`，包含：
- 字段定义表（字段名、类型、含义、示例值、全局唯一标识）
- 类型规范（接口定义、响应结构）
- 命名风格（驼峰/下划线统一）

### 2. 提需求（对话 A）

```
/translate-requirement

我想做一个类似掘金的文章详情页，需要点赞收藏评论功能
```

AI 会追问细节，直到输出精确的需求规格说明。

### 3. 执行开发（对话 B）

在新对话中：

```
/frontend-standard

[粘贴对话 A 输出的需求规格说明]
```

AI 将按 14 步机械执行，每步完成后强制输出标记，遇到冲突立即停止。

## 文件说明

| 文件 | 作用 | 使用方式 |
|------|------|---------|
| `naming-convention.md` | 项目命名规范和字段契约 | 对话 A/B 都会加载 |
| `translate-requirement.md` | 需求精炼命令 | `/translate-requirement` |
| `frontend-standard.md` | 强制执行命令 | `/frontend-standard` |
| `开发历程.md` | 项目演进历史和踩坑记录 | 参考文档 |
| `*.mermaid` | 架构流程图源文件 | 参考文档 |

## 适用场景

- 个人全栈项目快速迭代
- AI 辅助的前端开发
- 需要前后端契约一致性的项目
- 受够了 AI 写的"半成品"代码

## 设计哲学

> **"让 AI 像机械执行流水线一样输出确定性结果，而不是每次都赌 AI 的灵感。"**

三个设计原则：

1. **契约优先** — 共享 `naming-convention.md`，所有 Agent 从同一份契约加载，不用重复定义
2. **不信任，只对照** — 每个 Agent 天生没有全局视野，用交叉校验强制它们互相对照
3. **实现方案不能出现模糊化** — 一个方案好不好，取决于你在讨论它的哪个阶段引入它
