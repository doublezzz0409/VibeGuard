从实践中发现文档设计漏洞的经验总结
经历的阶段
阶段 1：按文档执行，遇到 bug

我们按 backend-standard.md 和 frontend-standard.md 执行，遇到了实际报错：

start.bat 闪退，看不到错误信息
前端空白页面，Vite 报错 Failed to resolve import "./mocks/browser"
MSW 和后端同时运行时数据来源混乱
http://localhost:8000/ 返回 Not Found
阶段 2：修 bug，发现是"自己人打自己人"

修 bug 过程中发现：这些不是随机错误，而是前后端流程之间的设计冲突：

前端流程设计了 MSW，但没考虑和后端共存
后端流程设计了测试，但没考虑和前端契约一致
两个流程各自独立设计，没有交叉校验机制
阶段 3：反向审查文档，发现系统性漏洞

站在"后端做完会不会影响前端"和"前端做完会不会影响后端"两个方向，审查两份文档，发现了 6+8=14 个设计漏洞。

核心经验
1. bug 是表象，流程漏洞是根因

表象（bug）	根因（流程漏洞）
start.bat 闪退	启动脚本没有末尾 pause
前端空白	MSW 模块可能不存在但被引用
MSW 拦截后端请求	没有定义 MSW 禁用机制
后端返回 1 而非 "art-1"	没有要求 ID 前缀转换
Pydantic 返回 422 而非 400	校验规则和错误码规则冲突
每个 bug 背后都对应一份文档里"没写"或"写矛盾了"的规则。

2. 单向流程能通过测试，交叉对接才会暴露问题

后端流程自己测试全部通过（56 个测试用例），但对接前端时 ID 格式、错误响应结构、字段命名都可能不一致。原因是：测试是自己写的，可以写成"通过"。只有引入前端契约（MSW mock 的响应结构）作为断言基准，才能真正保证一致性。

3. "默认值"和"优先级"是最容易遗漏的设计点

我们踩的坑几乎都和这两个概念有关：

MSW 和 Vite proxy 的优先级没有定义 → 请求被错误拦截
环境变量未定义时的行为没有定义 → 前端空白
Pydantic 校验和自定义错误码的优先级矛盾 → 返回 422
文档不能只写"怎么做"，还必须写"冲突时听谁的"和"不设置时默认什么"。

4. 最好的审查角度：假设自己是下游消费者

审查 frontend-standard.md 时，最有价值的提问是："后端做完后，前端会遇到什么问题？"审查 backend-standard.md 时，反过来问。这种角色互换的视角能发现单向审查看不到的盲区。

可复用的方法论
以后审查任何流程文档，可以用这四个角度：

默认值：不设置任何配置时，行为是什么？合理吗？
优先级：两条规则冲突时，听谁的？
反向影响：我做完后，下游（前端/后端/测试/部署）会遇到什么问题？
自检盲区：我的测试能自己写成通过，但能保证和外部契约一致吗？
